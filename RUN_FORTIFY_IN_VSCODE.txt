================================================================================
FORTIFY - RUNNING THE FRONTEND AND BACKEND IN VS CODE (WINDOWS / PowerShell)
================================================================================

What this file is
-----------------
A copy-paste guide to get FORTIFY running on your own machine, in two VS Code
terminals, so you can demonstrate it to another person.

Every command in the "verified" blocks below was executed against this
repository on Windows with PowerShell as the shell. Where a command was NOT
executed here, the block says so explicitly instead of pretending.

Product scope, so the demo is described honestly
------------------------------------------------
FORTIFY is a privacy-conscious, human-in-the-loop WELFARE DECISION-SUPPORT
PROTOTYPE built on SYNTHETIC data. It is not a medical, psychiatric or
disciplinary system and it does not prove anything about a real person.
Real departmental data is not present in this repository, and real-world
predictive validity has NOT been demonstrated. See docs/PRODUCTION_READINESS.md.

The default demo mode has NO real authentication. It trusts two request headers.
Do not expose it to an untrusted network. A production OIDC/JWKS bearer adapter
exists and is tested with locally generated keys, but a real department IdP
round trip, provisioning, MFA/session/logout, and official claim policy are
unverified. (Security note at the end.)

2c. Generate the demo data and models  (REQUIRED on a fresh clone)
--------------------------------------------------------------------------------
    python scripts\build_all.py

This is the deterministic pipeline: synthetic personnel and operational events
-> features -> personal baselines -> model -> calibration -> risk decisions ->
recommendations -> feasibility -> review queue -> demo case seeding. Seed is
pinned at 42, so the output is reproducible.

  MEASURED ON THIS MACHINE: 449.0 s (7 min 29 s) in a clean-tree reproduction
  on 2026-10-19; 421.4 s in an earlier working-tree run; 606.7 s (10 min 7 s)
  when the test suite and Docker were competing for the same disk. Exit code 0
  in all runs, Python 3.13 / Windows.
  Writes ~448 MB into data/generated/ (the largest single file is
  person_day_features_baseline.csv at ~204 MB) plus models and reports in
  artifacts/. README quotes ~448 MB; this matches the latest measured build.

  Per-step, so you know where the time goes (measured, same run):
      generate_synthetic_data.py    19.7 s
      build_features.py            291.5 s   <- 69% of the total, be patient
      build_baselines.py            16.4 s
      train_model.py                21.8 s
      build_phase5_risk_layer.py    18.7 s
      build_review_queue.py          1.9 s
      build_interventions.py        26.0 s
      build_feasibility.py          22.2 s
      prepare_demo.py                3.3 s

This step is the slow one. It is NOT needed again unless you delete the
generated files, change a pinned dependency version, or change the generator.
Section 5 ("After first setup") does not repeat it.

NOTE: build_all.py ends by re-running prepare_demo.py. That materializes any new
alert-policy cases into the configured workflow store and rewrites the demo
manifest; it does NOT reset the state of cases a human has already acted on.
Untouched NEW cases that are no longer in the regenerated queue are pruned
(rows with transition history, support events or feedback are permanent). If
you want a pristine demo, use a separate database/runtime directory via
FORTIFY_DATABASE_URL and FORTIFY_RUNTIME_DIR rather than deleting the live one.

You will know it worked when the last lines read something like (the seconds
vary by machine and disk load):

    PIPELINE COMPLETE in 449.0s
    Next: start the backend (see README) and open the frontend.

and you can see the files:

    ls data\generated\duty_events.csv
    ls artifacts\phase4\model_metadata.json

3. TERMINAL 1 - BACKEND (leave this terminal running)
================================================================================
Working directory: REPOSITORY ROOT.
The backend is started from the repo root with `--app-dir backend`; you do NOT
need to cd into backend\.

    python -m uvicorn app.main:app --app-dir backend --port 8000 --host 127.0.0.1

Why `python -m uvicorn` and not plain `uvicorn`: both were tested on this
machine. Inside an activated `.venv` the bare launcher exists
(`.venv\Scripts\uvicorn.exe`) and works. On this machine's GLOBAL interpreter the
`uvicorn.exe` shim is not present on PATH, so `uvicorn ...` fails with
"command not found" unless you activated a venv first. `python -m uvicorn` works
in both situations, so this file uses it throughout.

Verified in the test venv: `python -m uvicorn --version` ->
"Running uvicorn 0.52.4 with CPython 3.13.7 on Windows".

Expected success indication (the run stays in the foreground):

    INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
    INFO:     Application startup complete.

Do not close this terminal. Open a NEW terminal (the + button in the panel) for
step 4.

If the app starts but the data endpoints return HTTP 503, the generated files
are missing - run 2c. `/ready` names the exact missing artifact.

Demo note - the role is fixed at BUILD time, not login time:
  The frontend sends one role for the whole session, from VITE_FORTIFY_ROLE
  (default WELFARE_OFFICER). With the default you CANNOT open the Governance
  page: it calls audit and system-health endpoints that require the AUDITOR role,
  and correctly shows an "Access restricted" panel. (Verified: the panel is
  honest, it does not fake a pass or a failure.) To demonstrate the auditor
  view, stop the frontend and start it with the role set:

      $env:VITE_FORTIFY_ROLE = "AUDITOR"
      $env:VITE_FORTIFY_PURPOSE = "AUDIT"
      npm run dev

  VERIFIED OUTPUT of that command on this machine - the Governance page then
  renders:

      Audit chain            Verified
      25 events in current view · 4937 total in log
      Audit chain is intact.
      Access controls        Prototype role/purpose headers (not authenticated)
      Authentication         None (header-trust prototype)

  and the recent-events table lists the ALLOWED and DENIED access decisions,
  including the refusals produced by the role checks.

  (unset with `Remove-Item Env:VITE_FORTIFY_ROLE` when you go back). This is
  presentation switching for a demo, NOT authentication - see the security note.

Demoing unit scoping (new in this build) - backend side, no rebuild needed:

  Person-level access is now restricted to an explicit list of unit ids. Out of
  the box the demonstration runs with the named permission `demo:all-units`, so
  you see everything. To show the guard working, restart the backend scoped to
  two real units from the dataset:

      $env:FORTIFY_DEMO_UNIT_SCOPE = "U-011,U-012"
      python -m uvicorn app.main:app --app-dir backend --port 8000 --host 127.0.0.1

  What changes on screen - VERIFIED IN THE BROWSER on this build (scoped to
  U-011,U-012 and compared with the all-units default):
    * Attention header reads "49 synthetic personnel" instead of 500, and the
      queue shows 23 cases (12 needs attention, 11 worth checking) instead of the
      full 183. These are the same two units' people, not a broken page.
    * The Unit filter lists ONLY U-011 and U-012. Nothing from another unit
      appears in options, counts, totals or search results.
    * Opening a person outside your scope shows the honest error panel
      "We couldn't load this view / Personnel record not found" with a working
      Try again control. The page does NOT blank out, and the browser console has
      no unhandled exceptions - only the expected 404 network entries.
    * A mutating request against another unit's case is refused even when the
      request carries the correct current state.
    * Deliberate: the out-of-scope answer is the SAME status and the SAME text as
      a genuinely nonexistent id. That is what stops the profile endpoint being
      used to discover which personnel ids exist, so it is a feature, not a bad
      error message.
  To demonstrate the fail-closed rule, set an empty or nonsense value:

      $env:FORTIFY_DEMO_UNIT_SCOPE = ""          # or "U-***"  -> no person access

  Simplest way to run this demo without touching ports: stop the backend, set
  FORTIFY_DEMO_UNIT_SCOPE, and start it again on 8000 exactly as in Terminal 1.
  The proxy keeps everything same-origin, so you do not have to think about CORS.
  Two things this scope is NOT: it is not authentication (headers still decide
  the role), and it does not apply to a verified identity. A real OIDC token is
  scoped only by its own claims and ignores FORTIFY_DEMO_UNIT_SCOPE entirely;
  `demo:all-units` can never widen a verified identity, and
  `FORTIFY_AUTH_MODE=production` still refuses to boot without a real provider.

6a. Is it actually healthy? (run while the backend is up)

PowerShell-native, no curl alias surprises:

Expected /health:   {"status":"ok","service":"FORTIFY","version":"0.2.0"}
Expected /version:  {"service":"FORTIFY","version":"0.2.0"}

/ready is the one that matters before a demo. It reports three independent
layers so a healthy process cannot hide missing data:

    {"ready":true,
     "system":{"database":"ok"},
     "data":{"artifacts":"ok","data_quality":"ok","missing_artifacts":[], ...},
     "model":{"ready":true,"failed_checks":[],"checks_run":5, ...}}

`ready:false` returns HTTP 503 and names what is missing plus the command that
fixes it. Expect one standing data-quality WARNING: the synthetic world ends on
a fixed date, so as real time passes "latest event is N days old" grows. It does
not make /ready false and it is not a defect; it is the demo data being static.

/metrics is Prometheus text format (aggregate counters only, no person-level
data). PowerShell 5.1 needs -UseBasicParsing for non-HTML responses, otherwise
Invoke-WebRequest throws a NullReferenceException on .Content:

    (Invoke-WebRequest http://127.0.0.1:8000/metrics -UseBasicParsing).Content

Verified on this machine: /health, /version, /ready and /metrics all answer via
Invoke-RestMethod / Invoke-WebRequest -UseBasicParsing, and /ready reports
ready=True with system.database=ok, data.artifacts=ok, data_quality=ok,
model.ready=True across 5 checks.

7. STOPPING EVERYTHING
================================================================================
In each terminal press  Ctrl+C . Uvicorn prints "Shutting down" and exits; Vite
exits immediately.

To find and stop anything left holding a port:

    Get-NetTCPConnection -LocalPort 8000 -ErrorAction SilentlyContinue |
        Select-Object -ExpandProperty OwningProcess |
        ForEach-Object { Get-Process -Id $_ }

    Stop-Process -Name python -WhatIf     # preview first, then drop -WhatIf

Prefer -WhatIf before you actually kill anything: it prints what WOULD be
stopped. Do not use a blanket Stop-Process on node without checking, it will
take down unrelated tooling.


================================================================================
8. TROUBLESHOOTING
================================================================================
8.1 "can't open file '...build_all.py'" or "'scripts' is not recognized"
    You are in the wrong directory. These scripts must be run from the
    REPOSITORY ROOT, not from backend\ or frontend\. Check with Get-Location;
    `ls` should show README.md next to backend and frontend.

8.2 Port 8000 already in use ("[Errno 10048] ... address already in use")
    PREFERRED FIX: free the port (section 7) and stay on 8000. The Vite dev
    server proxies /api and /health to 8000 by configuration, so with the proxy
    path the browser only ever talks to one origin and nothing else must be set.

    If you genuinely cannot use 8000, you must change TWO things, not one:

        python -m uvicorn app.main:app --app-dir backend --port 8010 `
            --host 127.0.0.1
        cd frontend
        $env:VITE_API_BASE_URL = "http://localhost:8010"
        npm run dev

    ...and the backend must be told to accept that browser origin, because once
    you set VITE_API_BASE_URL the requests stop going through the proxy and
    become cross-origin:

        python -m uvicorn app.main:app --app-dir backend --port 8010 `
            --host 127.0.0.1
        # start it as, instead, setting the env first:
        $env:FORTIFY_CORS_ORIGINS = "http://localhost:5173"

    VERIFIED FAILURE IF YOU SKIP THAT: the frontend renders "We couldn't load
    this view / Could not reach the FORTIFY backend" and the browser console shows
    "blocked by CORS policy: Response to preflight request doesn't pass access
    control check: No 'Access-Control-Allow-Origin' header". The API itself is
    fine - curl to the same URL returns 200, which is exactly why this looks like
    a backend bug and isn't. Set FORTIFY_CORS_ORIGINS to the origin the browser is
    actually on (see 8.3 - it may not be 5173), and restart the backend.

    Note the proxy in frontend\vite.config.ts is hardcoded to 8000 and has no
    environment override, which is why moving ports forces you onto the
    cross-origin route above.

8.3 Port 5173 already in use
    Vite prints a different port, e.g. "Local: http://localhost:5174/" and you
    must open THAT address. Two consequences:
      * If you keep the proxy (no VITE_API_BASE_URL), nothing else changes - the
        proxy is server-side and the browser stays same-origin.
      * If you ARE using VITE_API_BASE_URL, the browser origin is now 5174, so
        FORTIFY_CORS_ORIGINS must include http://localhost:5174, not the default
        5173. This combination fails confusingly if you forget it (see 8.2).
    To force a specific port instead:  npm run dev -- --port 5173 --strictPort
    (with --strictPort it refuses to start rather than silently moving, which is
    easier to reason about during a demo).

8.4 Activation blocked: "running scripts is disabled on this system"
    PowerShell blocks the activate script by policy. Two options, least
    invasive first - change only your own account's policy, and only if you
    understand what RemoteSigned means on your machine:

        Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

    Or skip activation entirely; it is convenience, not a requirement:

        python -m pip install -r backend\requirements.txt
        python -m uvicorn app.main:app --app-dir backend --port 8000

    Or call the batch shim from cmd.exe:  .\.venv\Scripts\activate.bat

8.5 "ModuleNotFoundError: No module named 'fastapi'" (or uvicorn, pandas, ...)
    You are using an interpreter that does not have the pinned packages. Run
    `python -m pip install -r backend\requirements.txt`, and confirm you are in
    the venv you created (`python -c "import sys; print(sys.executable)"`).

8.6 The pages load but show no data, or a red error panel
    In order of likelihood:
      a. The backend is not running. Check http://127.0.0.1:8000/health .
      b. The generated data is missing. Check http://127.0.0.1:8000/ready -
         it names the missing artifacts. Fix: python scripts\build_all.py
      c. You started the frontend from the wrong folder, so the /api proxy has
         nothing to forward to. Start Vite from frontend\.
      d. You are looking at a page that needs the AUDITOR role (Governance).
         See the demo note in section 4. That panel is deliberate, not broken.

8.7 "npm install" fails or hangs
    Close VS Code's terminal, then in a plain PowerShell window:

        cd frontend
        Remove-Item -Recurse -Force node_modules, package-lock.json -ErrorAction SilentlyContinue
        npm install
        npm run build

    package-lock.json is version-controlled; deleting it locally loses nothing
    but determinism, so re-add it with `git checkout -- frontend/package-lock.json`
    before committing anything.

8.8 Database path problems ("unable to open database file")
    The SQLite file lives at backend\fortify.db and is created on first run. The
    location is resolved from the REPOSITORY ROOT, not your current directory,
    which is why running from repo root is required. To put it elsewhere:

        $env:FORTIFY_DATABASE_URL = "sqlite:///C:/some/dir/fortify.db"

    It is gitignored - never commit a .db file. If a demo database is wedged,
    stop the backend and delete backend\fortify.db; it rebuilds itself from the
    generated queue on next start (you lose the demo's review decisions).

8.9 /ready returns 503
    Read the JSON: it separates the three layers and names the failure.

      system.database not ok -> the DB is unreachable (permissions/path).
      data.artifacts  not ok -> generated files missing -> python scripts\build_all.py
      model.ready     false  -> model artifacts missing/incompatible -> re-run 2c,
                                and see scripts\promote_model.py before assuming
                                the model is "broken"; a stale registry can hold a
                                model id whose files no longer exist.

    The remedy string is printed for exactly this reason. Fix the named layer,
    then re-check /ready; you do not need to restart the backend for data files
    to be re-read.

8.10 A validator printed a traceback ending in UnicodeEncodeError
    If you hit this on this checkout, please report it - it was a known failure
    class (a gate script containing a "->"-style arrow as a real Unicode arrow
    character crashes when Python prints to a Windows cp1252 console) and is
    fixed plus regression-gated in scripts\validate_hardening.py. The safe
    workaround for any such script is:

        $env:PYTHONIOENCODING = "utf-8"

8.11 Everything looks fine but the demo numbers seem stale
    The synthetic world is fixed-date and ends on the last generated day
    (2026-06-29 for the standard 500 x 180-day build). "Updated <date>" on the
    Attention page is the data day, not today. That is expected for a seeded
    demonstration dataset.

8.12 "No module named uvicorn" right after you created a venv
    Two separate causes, both hit during this audit:

    a) The venv is brand new and has no packages in it. Activating a venv does
       NOT install anything. From the repository root, while the prompt shows
       the venv name:

           pip install -r backend\requirements.txt

       Check what the interpreter actually is, because the prompt can lie:

           python -c "import sys; print(sys.executable)"

    b) A venv created in the WRONG FOLDER. `python -m venv .venv` makes one
       relative to wherever you are, so running it from backend\ produces
       backend\.venv, which VS Code may then auto-activate while you still need
       to be at the repository root. Prefer one venv at the repository root and
       create it from there. If you already made backend\.venv and want to stop
       using it:  deactivate   then   Remove-Item -Recurse -Force backend\.venv

    Either way the backend command must be started from the REPOSITORY ROOT -
    `--app-dir backend` is resolved against your current directory, so running
    it from inside backend\ looks for a non-existent backend\backend.

8.13 The app is slow to respond, or the first page load crawls
    Measured on this machine with warm caches, the API is fast: /health ~5 ms,
    /api/dashboard/overview ~30-45 ms, /api/workflow/pending ~19 ms,
    /api/dashboard/person/<id> ~45 ms, /ready ~560 ms (it re-audits data quality
    on every call by design), and the Vite dev server serves modules in ~5-10 ms.

    If it feels much slower than that, the cause is usually contention rather
    than the application:
      * `python scripts\build_all.py` rewrites roughly 448 MB. Running the
        backend, the frontend, or a demo WHILE it regenerates is genuinely slow,
        and the data endpoints can even see half-written artifacts. Let it finish.
      * The full test suite, the validators, Docker builds and the pipeline all
        read those same large CSVs; several at once saturates one disk.
      * Windows Defender scans freshly written large CSVs and new Python
        processes; the first run after a regeneration is the slowest.
      * The first browser load pays Vite's on-demand transform of ~638 modules.
        Later loads are cached and fast; `npm run build` proves the production
        bundle is not affected.
      * If this repository sits inside a OneDrive folder, syncing 448 MB of
        changed files will dominate disk I/O. Pausing OneDrive during a
        regeneration, or keeping the working copy outside the sync root, is the
        practical fix.
    Do not solve this by making the app poll less often or by caching results it
    has to recompute; the numbers above show the request path is not the problem.

9. OPTIONAL: DOCKER (one command, but NOT the fast option)
================================================================================
Read this before choosing Docker over sections 3+4.

docker-compose.yml defines THREE services, and the first one is the whole data
pipeline:  pipeline  runs `python scripts/build_all.py` into named volumes and
must complete successfully before  fortify-backend  starts, which must become
healthy before  fortify-frontend  starts. So the FIRST `docker compose up
--build` is two image builds PLUS the ~7-minute regeneration measured in 2c.
Use the two-terminal path (sections 3 and 4) when you want a quick demo, and
Docker when you want to prove the containerised stack.

    docker compose up --build

Then open http://localhost:5173 - nginx serves the built SPA and proxies /api
and /health to the backend container (host port 8000). The workflow database
inside the containers is at /app/data/runtime/fortify.db, NOT backend/fortify.db,
because the image tree is read-only for the runtime user.

Both published ports are bound to 127.0.0.1, so the stack is reachable from this
machine only. That is deliberate: the demo API trusts X-Fortify-Role /
X-Fortify-Purpose headers, so anyone who can reach the port can pick their own
role. Do not change the mapping to "8000:8000" on a shared network without an
authenticating proxy in front; scripts/validate_hardening.py fails CI if the
mapping stops being loopback-only.

Stop and remove the stack:

    docker compose down

To also discard the demo data and database volumes:  docker compose down -v

10. SECURITY NOTE - READ BEFORE YOU DEMO TO ANYONE OUTSIDE YOUR OWN MACHINE
================================================================================
* The default demo mode authenticates nothing. It trusts the X-Fortify-Role and
  X-Fortify-Purpose request headers, and the frontend fills them from build-time
  environment variables. Anyone who can reach the port can set them to anything.
  This is a demonstration convenience, NOT access control. FORTIFY_AUTH_MODE=
  production requires OIDC bearer validation (implemented), but that path has
  not been exercised against a real department identity provider.
* Object-level unit scope IS enforced (see section 4) - but do not confuse the
  two. Scope decides WHICH units' people a caller may touch; it does not decide
  WHO the caller is. Because the role header is self-asserted, an attacker on the
  network can simply claim a role and, under the default demo configuration, the
  all-units permission. The scope check is real code and is tested; the identity
  behind it is not. Never treat this as authorization for real personnel data.
* The sidebar says "Not authenticated" and the Governance page reports the same.
  That label is accurate. Do not describe this build as authenticated.
* FORTIFY_AUTH_MODE=production fails closed without a configured issuer,
  audience and JWKS. The OIDC/JWKS adapter is implemented and tested with local
  keys, but no real identity provider has been connected, provisioned, or
  exercised for MFA/session/logout in this repository.
* Do not bind the dev server to 0.0.0.0, do not put it behind a public tunnel,
  and do not share it with the network during a demo. 127.0.0.1 is used
  throughout this file on purpose.
* The audit chain uses an HMAC key stored beside the runtime data
  (data/runtime/audit.jsonl.key). It is gitignored. It is a local demo key with
  documented limits, not a production secret; see docs/PRODUCTION_READINESS.md.
* The data is synthetic. No real personnel, unit or wellness records exist in
  this repository, and the model's reported metrics do not establish real-world
  predictive value.
