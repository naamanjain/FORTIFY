Summary: the prototype is **defensible as a demonstration and as an
engineering artifact**. The production blockers are exactly the ones stated:
real authentication, a production database deployment, backups, secret
management, and — before any operational welfare use — real-data validation
and governance sign-off.

## Evidence caveats (measured in this working tree, not asserted)

Numbers below were produced by running the named gate on this machine, and are
the ones a reviewer should re-measure rather than trust.

| Claim | What was actually measured | Limit |
|---|---|---|
| Red-team campaign holds | `pytest --red-team-report` -> **24 of 24 attacks held, 0 breached, 0 not executed** | Coverage gaps that used to SKIP are now built through the real endpoints (a case is driven to `SUPPORT_COMPLETED`, to a terminal `CLOSED` state, and a follow-up is scheduled and completed inside the test). A skipped attack is reported as NOT EXECUTED and is never counted as a pass. Attacks still run against the synthetic demo store with demo-wide scope; they have not been re-run against a real IdP-issued, unit-scoped identity. |
| Alert policy bounds case creation | `scripts/simulate_alert_fatigue.py` -> naive 45,744 threshold-day alerts reduced to **183 new cases**, 45,272 duplicates prevented, **289 budget suppressions recorded** | Synthetic 500 x 180-day world. Review capacity is assumed, not observed. |
| Model adds value | `scripts/validate_model_validity.py` -> leakage/contamination/temporal probes **PASS**; ROC-AUC 0.763. `scripts/benchmark_operational.py` -> temporal-score precision at top 1/2/5/10% review capacity **0.804 / 0.784 / 0.773 / 0.741** versus rule **0.745 / 0.784 / 0.706 / 0.647** | At the **deployed threshold point** the model scores F1 0.322 on the held-out window versus **0.614 for the two-variable operational rule**; on the shipped legacy demo generator the fitted model does not beat the rule at any capacity. On the benchmark-only latent generator it is 2–4 pp more precise at top 1–2%, while its ROC-AUC (0.711) is lower than the temporal score's (0.743). The model is a ranking signal at small review capacity, not a better thresholded classifier. Synthetic-only evidence. |
| Deterministic regeneration | `scripts/build_all.py` -> exit 0; three consecutive host runs of the queue builder were byte-identical. **The earlier cross-platform gap is now explained and closed.** Root cause: the review queue was only the visible symptom. All raw synthetic inputs were byte-identical between Windows and Linux (`personnel`, `units`, `duty/recovery/leave/deployment/training/incident/wellness_events`), the 100 numeric feature columns were bit-identical, but every one of the 90,000 model probabilities differed by up to **2.4e-3** - because `liblinear` was running at scikit-learn's default `tol=1e-4` and stopped well short of the unique optimum of this strictly convex problem. Two platforms therefore settled on two different "converged" models, flipping 60 `risk_level` assignments near the 0.33/0.66 band edges, which the alert policy amplified into 108 Windows-only and 82 Linux-only queue records. Fix: an explicit `ModelConfig.tolerance = 1e-10` with `max_iter` raised to 5000, passed to the estimator. Measured after the fix, on identical features in both environments: max probability difference **2.1e-7** (re-measured 2026-10-19 from full Windows and Linux pipeline runs: Windows Python 3.13.7, Linux Python 3.13.16, both pandas 2.3.3 / numpy 2.4.2 / scikit-learn 1.9.0), `risk_level` mismatches **0**, and the rebuilt `review_queue.csv` has the same 62,265 rows, the same record keys, and identical `case_created`, `suppressed_by_budget`, `alert_state`, `evidence_days`, `reason` and `risk_band` values row-for-row; the queue decision fingerprint is identical (`fcf41121197a7afb20263f5579eea144`). | Residual: scores still differ by up to ~2.1e-7 (platform libm/BLAS and optimizer-path rounding), so the CSV **bytes** are not identical even though every downstream decision is; in the measured full-pipeline comparison, **no** `risk_band` or `threshold_decision` value changed. Claim **"all downstream decisions reproduce cross-platform"**, not "byte-identical artifacts". Guards: `test_phase4_model.py` asserts the tolerance reaches the fitted estimator, that loosening it demonstrably changes the model, and that refits are bit-identical on one platform |
| Workflow and audit integrity | `verify_acceptance.py` **14/14**, `verify_workflow_lifecycle.py` **20/20**, `backup_restore_drill.py` **8/8 PASS**, chain valid after restore | SQLite demo store. PostgreSQL application path exercised by the live module (3 passed against disposable PG16); no departmental deployment or PostgreSQL restore drill. |
| Backend suite | `pytest -q` -> **332 collected: 328 passed, 4 skipped** on a freshly materialised store (2026-10-19, 112.6 s, Windows/Python 3.13); red-team report 24/24 PASS, 0 FAIL, 0 NOT EXECUTED. 3 skips are live-PostgreSQL tests that require `FORTIFY_TEST_POSTGRES_URL`; the 4th is the ingestion symlink-containment test, which skips only where Windows denies symlink creation (it runs on Linux). | Passing tests are not evidence about real personnel data, which this repository does not contain. The suite seeds non-`NEW` preconditions through the real transition endpoints instead of skipping. A green default run does not prove the PostgreSQL path. |

Model-promotion governance events (`MODEL_REGISTERED`, `MODEL_PROMOTED`) are now
written to the same HMAC-anchored chain the auditor reads. They previously went
to a second, unverified chain under `backend/data/runtime/`, so a promotion was
invisible to chain verification — if that split chain still exists in a
deployment, its two events must be re-anchored before the audit trail is treated
as complete.
