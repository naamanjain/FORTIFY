## Evidence caveats (measured in this working tree, not asserted)

Numbers below were produced by running the named gate on this machine, and are
the ones a reviewer should re-measure rather than trust.

| Claim | What was actually measured | Limit |
|---|---|---|
| Red-team campaign holds | `pytest --red-team-report` -> **24 of 24 attacks held, 0 breached, 0 not executed** | Coverage gaps that used to SKIP are now built through the real endpoints (a case is driven to `SUPPORT_COMPLETED`, to a terminal `CLOSED` state, and a follow-up is scheduled and completed inside the test). A skipped attack is reported as NOT EXECUTED and is never counted as a pass. Attacks still run against the synthetic demo store with demo-wide scope; they have not been re-run against a real IdP-issued, unit-scoped identity. |
| Alert policy bounds case creation | `scripts/simulate_alert_fatigue.py` -> naive 45,735 threshold-day alerts reduced to **183 new cases**, 45,263 duplicates prevented, **289 budget suppressions recorded** | Synthetic 500 x 180-day world. Review capacity is assumed, not observed. |
| Model adds value | `scripts/validate_model_validity.py` -> leakage/contamination/temporal probes **PASS**; ROC-AUC 0.763 | At the **deployed operating point** the model scores F1 0.322 on the held-out window versus **0.614 for the two-variable operational rule**. The model does not beat the rule at the operating point; it only edges ahead at a ~54% flag rate. Ranking is better than chance, not better than the simple baseline. |
| Deterministic regeneration | `scripts/build_all.py` -> exit 0; three consecutive host runs of the queue builder were byte-identical. **The earlier cross-platform gap is now explained and closed.** Root cause: the review queue was only the visible symptom. All raw synthetic inputs were byte-identical between Windows and Linux (`personnel`, `units`, `duty/recovery/leave/deployment/training/incident/wellness_events`), the 100 numeric feature columns were bit-identical, but every one of the 90,000 model probabilities differed by up to **2.4e-3** - because `liblinear` was running at scikit-learn's default `tol=1e-4` and stopped well short of the unique optimum of this strictly convex problem. Two platforms therefore settled on two different "converged" models, flipping 60 `risk_level` assignments near the 0.33/0.66 band edges, which the alert policy amplified into 108 Windows-only and 82 Linux-only queue records. Fix: an explicit `ModelConfig.tolerance = 1e-10` with `max_iter` raised to 5000, passed to the estimator. Measured after the fix, on identical features in both environments: max probability difference **2.0e-7**, `risk_level` mismatches **0**, and the rebuilt `review_queue.csv` has the same 62,265 rows, the same record keys, and identical `case_created`, `suppressed_by_budget`, `alert_state`, `evidence_days` and `risk_band` values row-for-row | Residual: scores still differ at ~3e-16 (platform libm/BLAS rounding), so the CSV **bytes** are not identical even though every decision is. Claim **"all downstream decisions reproduce cross-platform"**, not "byte-identical artifacts". Guards: `test_phase4_model.py` asserts the tolerance reaches the fitted estimator, that loosening it demonstrably changes the model, and that refits are bit-identical on one platform |
| Workflow and audit integrity | `verify_acceptance.py` **14/14**, `verify_workflow_lifecycle.py` **20/20**, `backup_restore_drill.py` **8/8 PASS**, chain valid after restore | SQLite demo store. PostgreSQL claims in this file were verified in an earlier session on a container that is not running here. |
| Backend suite | `pytest -q` -> **271 passed, 2 skipped** | Passing tests are not evidence about real personnel data, which this repository does not contain. |

Model-promotion governance events (`MODEL_REGISTERED`, `MODEL_PROMOTED`) are now
written to the same HMAC-anchored chain the auditor reads. They previously went
to a second, unverified chain under `backend/data/runtime/`, so a promotion was
invisible to chain verification — if that split chain still exists in a
deployment, its two events must be re-anchored before the audit trail is treated
as complete.
